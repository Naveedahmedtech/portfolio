# SECOND_SECTION.md

## Purpose

The second section translates the hero positioning into concrete engineering areas.

The hero says:

> I build backend systems that connect products, developers, data, and AI.

This section proves what that means before the visitor enters the detailed Rasterex and PlayLight case studies.

It should communicate engineering breadth without becoming a generic skills section.

---

# Section Role

This section should answer:

```text
What does Naveed actually build?

What kinds of engineering problems does he work on?

Where is his strongest experience?
```

The answer should be immediately understandable:

```text
Backend Systems
Developer Platforms & SDKs
Integrations
AI-enabled Backend Products
Production Engineering
```

---

# Section Eyebrow

Recommended:

```text
WHAT I BUILD
```

Alternative:

```text
ENGINEERING FOCUS
```

Prefer:

**WHAT I BUILD**

It is more direct and less résumé-like.

---

# Main Heading

Recommended:

# Backend engineering across product, platform, and production boundaries.

Alternative:

# I work where application logic meets APIs, infrastructure, developer experience, and data.

Preferred:

**Backend engineering across product, platform, and production boundaries.**

It reinforces the hero without repeating it.

---

# Supporting Copy

Recommended:

> My work is centered on building the systems behind products — APIs, SDKs, integrations, data flows, background processing, and AI-enabled backend features. I care about the boundaries between systems: how they communicate, fail, scale, and remain understandable to the developers using them.

Keep this concise.

Do not list every technology here.

---

# Core Engineering Areas

Use **four areas**.

Do not create eight or ten skill cards.

Recommended structure:

```text
01 Backend Systems
02 Developer Platforms
03 Integrations
04 AI Backend
```

---

# 01 — Backend Systems

## Title

**Backend Systems**

## Copy

> APIs and application services built around clear contracts, reliable data flows, authentication, persistence, asynchronous work, and production failure handling.

## Supporting Technologies

Keep visually secondary:

```text
Node.js · TypeScript · NestJS · PostgreSQL
```

## Visual Motif

Simple request path:

```text
Request
   ↓
API
   ↓
Service
   ↓
Database
```

Motion can show a single request moving through the path.

---

# 02 — Developer Platforms

## Title

**Developer Platforms & SDKs**

## Copy

> Developer-facing APIs, npm packages, integration contracts, documentation, and tooling designed to make complex products easier to embed and operate.

This is particularly important because it leads naturally into Rasterex.

## Supporting Concepts

```text
SDKs · npm packages · API contracts · Developer Experience
```

## Visual Motif

```text
Application
     ↓
    SDK
     ↓
Platform
```

This should visually hint at the Rasterex architecture that appears in the next major section.

---

# 03 — Integrations

## Title

**Integrations**

## Copy

> Systems that connect products across browser boundaries, external APIs, payments, scheduling platforms, and customer environments.

## Supporting Concepts

```text
PostMessage · REST APIs · Stripe · Calendar / Meeting APIs
```

Do not turn this into an integration-logo wall.

## Visual Motif

Multiple systems connected through one integration layer:

```text
System A ──┐
           │
System B ──┼── Integration Layer
           │
System C ──┘
```

**AI-enabled Backend Systems**

## Supporting Technologies

## Visual Motif

# Desktop Composition

A stronger interactive version can use:

```text
LEFT                         RIGHT

01 Backend Systems          live technical visual
02 Developer Platforms      that changes according
03 Integrations             to active item
04 AI Backend
```

The left list drives the visual on the right.

As the visitor scrolls through each engineering area, the right-side system diagram evolves.

This fits the continuous motion direction of the site.

or visually transition back toward it.

# Technology Treatment

Technologies should be supporting evidence only.

Bad:

```text
NODE
TYPESCRIPT
NESTJS
POSTGRES
REDIS
AWS
DOCKER
...
```

Good:

```text
Backend Systems
Node.js · TypeScript · NestJS · PostgreSQL
```

The reader should remember the **engineering capability**, not just the tool names.

# What Not to Include

Do not use:

* skill percentage bars
* proficiency ratings
* 20 technology logos
* “What I do” freelancer service cards
* frontend development as a primary category
* UI/UX design
* generic “clean code” card
* artificial statistics
* exaggerated production claims
* long paragraphs

This section is about **engineering capabilities**, not services being sold.
